# 推荐方案（2026-10-27 第二批后）

> 结论先行：**先修前端，再谈翻译。**
> 现在数据已经"满"到 1212/1217 集有剧情、149 案有完整 L3，但**用户在页面上什么都看不到**——
> 剧集卡片全部显示 `[object Object]`，案件详情页一个剧情字段都不渲染。
> 继续堆数据的边际价值接近 0，把这批数据变成可见内容的价值最大。

## 一、必须先说的两个实测问题

### 1. `[object Object]` —— 1212/1217 集现在就坏着

`app.js:112`：

```js
intro: record.summary || details || '目录条目已收录…'
```

`summary` 自上一批起已经是对象（`{en, zhHans, zhHant, sourcePage…}`），
`escapeHtml()` 里 `String(value)` 把对象变成 `[object Object]`。

实测（node）：

```
summary 类型: object
intro 渲染结果: [object Object]
会渲染成 [object Object] 的剧集数: 1212 / 1217
```

**这不是本批引入的**（上一批 `backfill-episode-summaries.py` 把 summary 改成 dict 时就坏了），
但本批把 614 集从"空（走 fallback）"填成了"有对象（直接坏）"，所以**症状范围被放大了**。
修它只需一个取词函数，成本 10 分钟，收益是整个站点。

### 2. 案件详情页不显示任何剧情字段

`app.js:235 detailSections()` 对 `type === 'entity'` 只渲染：
档案状态 / 身份职能 / 别名 / 案件类型 / 动画范围 / 漫画范围 / 关联人物 / 使用者 / 成员 / 关系 / 关联案件 / 关联主线 / 关联地点。

**`summary` / `culprit` / `motive` / `method` / `evidence` / `resolution` 一个都没有。**
也就是说：243 条凶手、149 套 L3 字段、2507 条角色挂接，在页面上全部不可见。

## 二、推荐路线（按投入产出排序）

### P0 · 修前端（0.5–1 天，最高优先）

| # | 改动 | 文件 | 验收 |
|---|---|---|---|
| 1 | 加 `textOf(field)`：`zhHans → zhHant → ja → en → 字符串兼容 → ''` | `app.js` | node 断言全库无 `[object Object]` |
| 2 | 剧集 intro / 详情页改用 `textOf(record.summary)`；空则走原 fallback | `app.js` | 卡片与详情页出现真实剧情 |
| 3 | 案件详情页加「深度剧透」分区：summary、犯人、动机、手法、证据、结局；按 `spoiler` 等级折叠，`lang=en` 的字段挂 `EN` 角标 | `app.js` + `styles.css` | 打开月影岛案能看到全部五个字段 |
| 4 | 「详情完成度」改为按「是否有 zhHans」判定，不再用 `raw.summary ?` 的真值判断 | `app.js` | 中文缺口的条目显示「英文原文 · 待译」 |

> 为什么排第一：数据已经领先前端一大截，这一小时能把已有资产直接变现；且 `[object Object]`
> 是当前最刺眼的缺陷，任何审核都会第一眼撞上。

### P1 · L3 字段双语化（0.5 天，一次性迁移）

**问题**：案件字段是纯字符串，288 条中文（242 culprit + 46 手工 L3）和 422 条本批写入的英文
混在同一层，谁也分不出哪条是什么语言、翻译没翻译。

**方案**：把字段升级为带语言的对象，与项目既有的 `title`/`summary` 约定一致。

```json
"culprit": {
  "zhHans": "浅井成实，真实身份为麻生成实；以女性身份在月影岛行医。",
  "en": "Asami Keisuke (real name: Narita Seiji) ...",
  "translationStatus": "human"        // human | machine | pending
}
```

- 迁移脚本（幂等、带备份、出报告）：
  - 纯字符串中文 → `{zhHans: 原值, en: dcwL3Source.en 或 null, translationStatus: "human"}`
  - 本批英文 → `{zhHans: "", en: 原值, translationStatus: "pending"}`
- `validate-data.py` 增加结构校验（允许 string 与 object 并存一段时间，但新增必须 object）。
- 前端 `textOf()` 已兼容，迁移不阻塞页面。

> 好处：**一句原文都不丢**，也不会假装中文已经完成；以后补中文只是往里写一个键。

### P2 · 翻译流水线（分批，每批 20 案，可无人值守）

1. 生成 `docs/TRANSLATION-QUEUE.md`：149 案 × 4–5 字段，按「主线相关度 + 案件知名度」排序
   （月影岛、外交官、图书馆这类先译，路人原创集往后排）。
2. 每批执行：我逐条对照 `dcwL3Source.<field>.quote` 的**英文原文**译成中文 →
   写入 `zhHans` → `translationStatus: "machine"`、`reviewed: false`。
3. 产出每批 diff 报告 + 高风险清单（人名、双关、日文梗、双凶手），你只抽检这些。
4. 用 cron 每 30 分钟跑一批，无人值守；每批零改动则自动停（幂等自检）。

> **为什么这是唯一诚实的路径**：不翻译就只能留英文；而"凭印象写中文"等于二次创作。
> 所以中文必须**逐条挂在英文原文引用上**，可对照、可回滚、可分级抽检。

### P3 · 剧集 summary 中文（不阻塞，按需）

- 1212 条英文，全量翻译是 180 万字级别，性价比最低。
- 推荐：**前端双语显示**（有中文显示中文，没有显示英文 + `EN` 角标），
  只翻译「主线篇 + 你点名的集」这类高价值子集。
- 这是**分工**，不是欠债：英文原文本身就是可核对的来源，留原状比机翻更可靠。

### P4 · 角色实体（等你拍板，建议保守）

- 建议只建「出现 ≥5 案」的 **119 个**：`name.en` + `caseRefs`（已有 2588 条挂接可直接用）
  + `sources` + `translationStatus: "pending"`，中文名留空。
- 不建议 388 个全建：`castNames` 里大量是一次性路人，「人物」分区会有 3/4 是无人认识的英文名。

### P5 · 收尾

- 5 集无正文（713/714/882/1061/1187）：等第二个可读来源，不按相邻集推断。
- EP.585 归属（Kirin's Horn vs Kobayashi）：二选一裁定，写进 `FACT-CONFLICTS.json`。
- `git init` + 首次提交 + 打 tag（迁移前先提交一次做 checkpoint，这点建议**现在**就做）。
